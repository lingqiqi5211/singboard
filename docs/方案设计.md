## 技术方案概述

面板沿用上游已有的 GitHub Release 自更新流程：启动时或用户手动检查最新稳定 Release，下载 `singboard.exe`，校验 GitHub 提供的 SHA-256 摘要，再通过独立更新进程替换并重启面板。本分支只调整发布源归属与发布约束，不另建一套更新器。

## 技术选型

| 类别 | 选择 | 理由 |
| --- | --- | --- |
| 更新源 | 构建时注入 `github.repository` | 构建产物自动跟随产生它的仓库，不允许运行时随意切换受信任的二进制来源 |
| 本地回退 | `lingqiqi5211/singboard` | 本地或非 GitHub Actions 构建仍能检查本分支的 Release |
| 版本发现 | GitHub `releases/latest` | 复用现有逻辑，只跟踪正式 Release，忽略草稿和预发布版本 |
| 发布资产 | `singboard.exe` | 与现有替换流程和 `build.yml` 产物名称一致 |
| 完整性校验 | Release 资产 SHA-256 digest | 下载后、替换前校验，镜像下载也不能绕过校验 |

## 方案比较

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 运行时允许填写仓库 | 最灵活 | 容易误装任意仓库的可执行文件，信任边界不清晰 |
| 在代码中固定本仓库 | 改动最少 | fork 或复制构建流程时容易忘记修改，后续同步上游也较脆弱 |
| 构建时注入仓库（采用） | 安全边界明确，适配 fork，维护成本低 | 发布前必须由 CI 正确构建 |

## 架构与数据流

1. GitHub Actions 构建时将 `${{ github.repository }}` 注入 `SINGBOARD_PANEL_UPDATE_REPO`。
2. Rust 后端使用该编译期值请求对应仓库的最新 Release；本地未注入时使用本仓库作为默认值。
3. 后端只选择名称精确匹配 `singboard.exe` 的资产，并把版本、发布时间、大小与摘要返回前端。
4. 用户确认后，后端重新读取 latest Release，要求资产地址、大小和摘要仍与检查结果完全一致；同时限制地址必须属于编译时绑定仓库，并要求提供 SHA-256 摘要。
5. 后端下载到临时目录，校验摘要，启动独立更新进程并退出当前面板。
6. 更新进程等待旧进程结束，备份并替换原文件；失败时恢复备份，成功后重新启动面板。

## 接口设计

现有 Tauri 接口保持不变：

- `check_panel_update`：检查编译时绑定仓库的最新正式 Release。
- `perform_panel_update`：使用检查结果中的资产地址、大小和摘要执行更新。
- `panel-update-progress`：报告下载、校验和替换阶段。

## 关键设计决策

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 更新源是否可由用户修改 | 否 | 面板更新会执行下载内容，应固定信任来源 |
| 是否另加定时轮询 | 否 | 保留已有“每次启动静默检查一次”和手动检查，避免无意义请求 |
| 标签与程序版本 | CI 强制一致 | 防止 Release 标签已升级但程序内部版本未升级，导致反复提示更新 |
| 没有 Release 时 | 明确报错，不回退上游 | 防止本分支用户意外切换回其他仓库的产物 |
